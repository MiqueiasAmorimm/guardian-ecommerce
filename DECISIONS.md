# Technical Decisions — Guardian

This document records the key architectural and technical decisions made while building Guardian, a microservices e-commerce platform (catalog, order and payment services).

Each decision lists the context, what was chosen, the alternatives considered and the trade-offs.

---

## Catalog service

### 1. UUID instead of Long as ID
- **Context:** each microservice has its own database. With sequential IDs, product `1` and order `1` can collide when data crosses services.
- **Decision:** UUIDs generated by the application.
- **Alternative:** sequential `Long` generated by the database.
- **Trade-off:** UUIDs never collide across services, but take more space and are harder to read than a sequential number.

### 2. Flyway instead of Hibernate `ddl-auto`
- **Context:** `ddl-auto=create` can drop tables and lose data.
- **Decision:** every schema change is a numbered SQL migration that runs once.
- **Alternative:** letting Hibernate generate the schema.
- **Trade-off:** more files to write, but every change is traceable and safe to apply.

### 3. Rich domain model
- **Context:** validation rules scattered across layers are easy to bypass.
- **Decision:** the `Product` entity validates name, description and price in its constructor, so the rules apply no matter who creates it.
- **Alternative:** a model with only getters and setters, with validation in services.
- **Trade-off:** the entity carries more logic, but invalid objects cannot exist.

### 4. Environment variables for credentials
- **Decision:** database credentials come from environment variables, with defaults for local development.
- **Alternative:** values hardcoded in `application.yml`.
- **Trade-off:** a bit more setup, but no secrets in source code.

### 5. Layered architecture
- **domain** → business rules, no external dependencies
- **application** → use cases, orchestrates the domain
- **infrastructure** → database access, technical details
- **web** → HTTP controllers, DTOs, error handling
- **Trade-off:** more packages and classes for a small service, in exchange for clear responsibilities and easier unit tests.

### 6. Pagination on `GET /products`
- **Decision:** returns products in pages instead of all at once.
- **Trade-off:** clients must handle pages, but the endpoint stays fast with large datasets.

## Order and payment services

### 7. Status as an enum with a transition validator
- **Context:** `Order.status` started as a raw `String`, with no closed set of valid values.
- **Decision:** an `OrderStatus` enum (`CREATED`, `AWAITING_PAYMENT`, `APPROVED`, `REJECTED`, `CANCELED`) and a separate `OrderStatusTransitionValidator` that defines the allowed transitions. `APPROVED`, `REJECTED` and `CANCELED` are terminal. Payments follow the same idea (`PENDING` → `APPROVED` / `REJECTED`).
- **Alternative:** keeping the `String` and validating in each place that changes it.
- **Trade-off:** more classes, but an order or payment can never jump to an invalid state.

### 8. Kafka for order → payment communication
- **Context:** an order should not wait for payment processing to finish.
- **Decision:** order-service publishes an `order.created` event and payment-service consumes it.
- **Alternative:** order-service calling payment-service directly over HTTP.
- **Trade-off:** services are decoupled and one can be down without blocking the other, but the flow is harder to debug and the result is eventually consistent.

### 9. Synchronous call to the catalog for prices
- **Decision:** order-service asks catalog-service for the product price over HTTP when creating an order, and calculates the total itself.
- **Alternative:** trusting the price sent by the client.
- **Trade-off:** order-service depends on catalog-service being available, but the client cannot manipulate prices.

### 10. Each service keeps its own copy of the event class
- **Context:** payment-service reads the event published by order-service.
- **Decision:** each service defines its own event class instead of sharing a library.
- **Alternative:** a shared module with the event contract.
- **Trade-off:** the contract is duplicated, but services stay independent and can ignore fields they don't need.

### 11. Lesson learned: the event carried the unit price
- **What happened:** the first version of `order.created` sent the unit price instead of the order total.
- **How it was found:** following the logs from order-service to payment-service.
- **Fix:** the event now carries the total (`price × quantity`).
- **Takeaway:** test the whole flow end to end, not only each service alone.
